# SteamWatch 2.0 重设计决策

本文件解释已确认的产品/技术方向和取舍，不保存动态进度。产品规则见 [PRD](product/PRD.md)，行为见 [SPEC](../SPEC.md)，页面细节见 [交互约定](design/interaction-contract.md)，实现见 [架构](architecture.md)。

## 方向与比较基线

继续 C#/.NET/WinUI 3，以 Windows 原生、本地离线、托盘常驻为定位。当前平台适合延续原生控件、通知与系统集成；本轮重点是状态职责、可维护性和统一体验，不因重写同步升级框架。1.2.0 比较能力/数据/效果，不冻结源码；UI、逻辑和数据模型可按明确收益重构，保护数据、认证和执行安全。

设计启动时 Shell 过于集中，游戏/规则重复入口、维护与帮助样式分散、绿色文件多且启动入口不清；历史源码行数、首轮截图及旧双标签草案只作为启动依据，原文存于 [重组记录](history/doc-migration-2026-10-12.md)。不把当时问题全部当作当前缺陷。

## 页面取舍

采用用户确认的第一版层级，游戏首页回答当前是否计时、日/周总预算、有效约束和最早强退。全局每日/每周都在顶部直接编辑；单游戏规则只在游戏库按目标编辑。独立规则页与库/规则双标签取消，避免重复配置面；双击与原生右键并保留按钮入口，目录外历史规则仍能管理。

统计明确实测/估算/合计及各自日期，七日图有数值等价入口；设置分即时与显式草稿，帮助直读且捷径只导航。统一视觉优先共享资源/平台控件；不为图表新增框架，不用大量装饰挤压列表。具体尺寸、主题、焦点和正文排版唯一来源为交互约定。

## 代码方向与质量取舍

Shell 负责导航、认证/对话框及退出协调，独立页面和纯状态对象承接交互；后台与页面生命周期分离，Runtime 单写入，展示用同代快照。避免把 partial 文件拆分等同于职责拆分，也不为抽象本身加组件。API/schema 可因收益调整，但行为变更同步 SPEC，数据变更有迁移/备份/中断恢复。

性能先同口径测量再优化；计量/保存/执行保护不因速度削弱。降低分配可接受有明确记录的耗时权衡，不将短测比例推广到整个应用。模块与算法实际落地细节集中在架构/数据模型，测量在性能报告。

## 安装与发布方向

目标 Inno 当前用户 EXE 和绿色 ZIP，程序/数据分离、旧格式复制迁移。Inno 接入自定义认证/保存/正常退出，禁绕过为直接关进程；先验证占用/注册失败/中断回滚，必要时保留受控更新助手。程序回滚与数据降级分别判断。

安装页应明确版本/范围/目录和完成后的启动入口，默认不新增自启；卸载默认保留数据，不加入一键删除全部数据。主程序/安装器/卸载器设计签名和时间戳，但必须有真实证书/结果；不承诺 SmartScreen 无警告。用户主动下载安装，首版不做静默自更新。细节见 [安装设计](installer-evaluation.md)。

## 完成定义

功能对照无遗漏、数据/保护不弱化、主题/缩放和焦点可用、安装系统闭环有证据。原生、合成、真实游戏、干净系统分别验证，不以一次构建或概念稿作为完成。阶段依赖与 WU 见 本地 `PLAN.md`，当前剩余边界只见 本地 `STATUS.md`。
